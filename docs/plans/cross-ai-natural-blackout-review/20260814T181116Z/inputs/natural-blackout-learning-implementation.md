# План: обучение модели на естественных блэкаутах

## 1. Цель

Сделать так, чтобы естественные отключения электричества приносили измеримую пользу:

1. каждое отключение надёжно сохраняется;
2. приложение явно сообщает, чему оно научилось или почему ничего не изменило;
3. каждый качественный разряд проверяет существующую физическую модель, а изменяет только тот
   параметр, для которого событие даёт независимое доказательство;
4. повторные длинные разряды позволяют замечать снижение доступного запаса батареи;
5. обычный блэкаут не выдаётся за лабораторное измерение абсолютной ёмкости;
6. обучение не может ослабить или задержать безопасное выключение сервера без отдельного
   доказанного решения.

Проект считается работающим только после доказанного пути:

```text
естественный блэкаут
  -> целостное событие на диске
  -> понятная оценка качества данных
  -> проверка прогноза и физических параметров
  -> изменение только доказуемого параметра либо recorded_only
  -> видимый пользователю отчёт
```

## 2. Что сейчас сломано

### Основной разрыв

- `DischargeCollector` закрывает все обычные события с
  `model_processing_eligible=False`.
- `DischargeHandler.apply_completed_discharge()` изменяет модель только для
  `controlled_capacity_test` с `model_processing_eligible=True`.
- Производственного кода, создающего такое событие, нет.
- Поэтому журнал уже работает, а обучение на естественных блэкаутах — нет.

### Опасные обходные пути

1. `SagTracker` изменяет `ir_k` и RLS по первому провалу напряжения после перехода на
   батарею. Сам код документирует, что это измерение смешивает внутреннее сопротивление,
   исчезновение зарядного напряжения и поверхностный заряд. Текущее значение уже достигло
   верхнего ограничителя `0.025`.
2. Планировщик всё ещё может отправить UPS команду короткого теста. Для безопасной разработки
   и первого выпуска он должен только предлагать тест, но не запускать его.
3. Нормально отклонённое обычное событие может оставаться в состоянии `pending_replay`, хотя
   повторная обработка никогда не сделает его допустимым.
4. При старте служба может сообщить готовность до первого успешного чтения физического UPS и
   обновления виртуального файла. После аварии там может лежать старое `LB`.
5. Боевой путь виртуального UPS всё ещё является библиотечным значением по умолчанию. Текущая
   защита pytest полезна, но правильный путь должен передаваться явно.
6. Нет явной защиты от двух процессов, одновременно пишущих модель, журнал или виртуальный UPS.

### Научные ограничения текущих расчётов

- Уровень заряда в журнале вычислен самой LUT. Его нельзя использовать как независимую
  правильную метку для обучения этой же LUT.
- `load %` UPS, преобразованный через номинальные ватты и напряжение, является только оценкой
  тока: он не учитывает собственное потребление UPS и потери инвертора.
- Разряд, закончившийся возвращением сети, не показывает, сколько батарея могла бы проработать
  до конца.
- Срабатывание виртуального `LB`, вычисленного самой моделью, не является независимым
  доказательством физической ёмкости батареи.
- Текущий `CapacityEstimator` возвращает заряд, отданный на наблюдавшемся участке, а не
  доказанную полную ёмкость батареи.
- Показатель Peukert нельзя вычислять из частичного разряда, завершившегося возвращением сети,
  как будто это было полное время работы.

## 3. Решения панели

### 3.1 Два независимых контура

Не расширять существующий флаг допуска до абсолютной модели. Вместо этого создать два
раздельных контура.

1. **Наблюдение и проверка на естественных блэкаутах**
   - история и счётчики;
   - наблюдавшаяся длительность и кривая напряжения/нагрузки;
   - отклонения фактической кривой от предсказанной;
   - кандидаты физических параметров только там, где данные действительно их определяют;
   - никаких заявлений об абсолютных Ah или SoH.

2. **Авторитетное измерение батареи**
   - абсолютная ёмкость, SoH и Peukert;
   - только при независимых и достаточных исходных данных;
   - контролируемый тест остаётся возможным источником, но не является обязательным для
     практической пользы проекта.

### 3.2 Не один boolean, а решения по каждому полю

Заменить смысл единственного `model_processing_eligible` небольшим неизменяемым объектом только
для реально реализуемого первого среза:

```python
@dataclass(frozen=True)
class LearningDecision:
    record_history: Decision
    record_model_residuals: Decision
    record_terminal_candidate: Decision
    propose_capacity_update: Decision
```

Каждый `Decision` содержит `allowed: bool` и короткий список причин. LUT, Peukert и IR не получают
заранее пустых полей: отдельное решение добавляется одновременно с первым рабочим сценарием для
конкретного параметра. Это исключает и общий флаг, и восемь декоративных ворот.

### 3.3 Классы естественных событий

| Класс | Минимальное значение | Что разрешено |
|---|---|---|
| `operational_short` | Переключение и несколько секунд наблюдений | История, количество переключений, точная наблюдавшаяся длительность |
| `operational_partial` | Не менее 5 минут, качественные точки, сеть вернулась | История, кривая, оценка отданного заряда с явной меткой `proxy`, проверка текущей модели без автоматического изменения |
| `operational_gapped` | Есть перезагрузка или неизвестный промежуток | История и известные отдельные участки; никакой интеграции через разрыв |
| `natural_policy_endpoint` | Система дошла до собственного безопасного правила выключения | Практический результат политики; не независимая ёмкость батареи |
| `natural_terminal_candidate` | Есть независимый физический признак конца и полный качественный путь | Кандидат доступного запаса при данной нагрузке; без независимой модели тока научная модель не меняется |
| `controlled_quick_test` | Встроенный короткий тест UPS | Проверка переключения и захвата; научная модель не меняется |
| `controlled_capacity_test` | Полные независимые условия протокола | Кандидат абсолютной ёмкости/SoH; Peukert требует дополнительных нагрузочных данных |

Закрытое событие всегда получает окончательный статус `applied`, `recorded_only` или
`rejected`. Обычное `recorded_only` не должно превращаться в вечный `pending_replay`.

### 3.4 Лёгкая доменная модель

Не делать полный DDD-переезд и не создавать framework из repositories, factories и services.
Нужны только границы, которые запрещают наблюдению, планировщику и safety-коду напрямую менять
модель.

#### Единый язык

- `UpsObservation` — один сырой ответ физического UPS с монотонным временем;
- `DischargeEvent` — завершённая последовательность наблюдений с lifecycle;
- `EvidenceAssessment` — класс доказательства, качество и причины;
- `BatteryModelSnapshot` — неизменяемые параметры, использованные для прогноза события;
- `ModelResiduals` — расхождение наблюдения и замороженной модели;
- `CapacityCandidate` — повторяемое наблюдение, ещё не имеющее права менять модель;
- `CapacityUpdateProposal` — предложение изменить принятую ёмкость с независимой моделью тока;
- `ModelDecision` — принято, отклонено или только записано, с причинами;
- `AppliedModelChange` — event ID, старое/новое значение и хеш сохранённой модели;
- `SafetyEstimate` — расчёт, используемый только для виртуального UPS и выключения.

Термины `actual runtime`, `measured capacity` и `measured SoC` запрещены, если событие не содержит
независимой правильной метки.

#### Границы ответственности

```text
NUT adapter
  -> Observation / Event Capture
       -> Event Journal
            -> Evidence Assessment
                 -> Model Evaluation
                      -> Candidate
                           -> Parameter Proposal, только при независимом доказательстве
                                -> Battery Model (единственный writer)

Observation + BatteryModelSnapshot
  -> Safety Policy
       -> Virtual UPS output
```

1. **Observation / Event Capture**
   - читает и нормализует NUT;
   - создаёт события и пишет журнал;
   - не импортирует `BatteryModel` и не имеет setters модели.
2. **Evidence Assessment**
   - чистая функция из завершённого события;
   - классифицирует данные и выдаёт решения по параметрам;
   - не читает и не пишет файлы.
3. **Model Evaluation**
   - сравнивает событие с неизменяемым снимком;
   - создаёт `ModelResiduals`, затем кандидата и только при независимых данных предложение;
   - не применяет изменение самостоятельно.
4. **Battery Model**
   - единственный владелец научного состояния;
   - применяет только разрешённые типы предложений;
   - делает один атомарный commit и event-ID dedup;
   - его внутренний dict недоступен остальным компонентам.
5. **Safety Policy**
   - использует только уже сохранённую проверенную модель;
   - не запускает обучение и не зависит от незавершённого journal replay;
   - единственная область, имеющая право формировать `LB`.
6. **Operations / Reporting**
   - отображает факты, решения, остатки и применённые изменения;
   - не принимает доменных решений.

#### Минимальные типы изменений

В первом срезе существуют только `CapacityCandidate`, `CapacityUpdateProposal` и отдельная
операторская команда `BaselineReset`. Общий union и типы для LUT/Peukert/IR появятся не раньше
второго реально реализуемого изменения.

`CapacityUpdateProposal` изменяет существующее поле `capacity_ah_measured`. В прогнозе остаётся
существующая физическая формула: rated capacity задаёт базу Peukert, а множитель `soh` становится
строго производным `clamp(capacity_ah_measured / rated_capacity_ah, 0, 1)`. Нельзя одновременно
подставить measured capacity как `capacity_ah` и ещё раз умножить её на SoH.

Переход выполняется без скачка прогноза: до первого авторитетного измерения используется текущее
значение `soh`; после принятия ёмкости SoH только отображает её отношение к rated capacity.
Автоматическое предложение может только уменьшить `capacity_ah_measured` и обязано доказать
golden-тестом, что при том же входе runtime/LB не сдвигается позже. Повышение ёмкости возможно
только через явный `BaselineReset` после замены батареи или отдельное авторитетное измерение.
Принятие снижения ёмкости никогда не устанавливает `new_battery_detected`.

#### Порты только на опасных границах

Интерфейсы нужны только для внешних эффектов:

- чтение NUT;
- append/replay журнала;
- атомарное сохранение модели;
- запись virtual UPS;
- отправка команды UPS.

Не создавать абстракции для чистых формул, dataclass и единственной реализации. Production
composition root явно передаёт все опасные пути и capability отправки команд. Тестовая сборка не
получает боевой путь и command capability в принципе.

#### Как переходить без большого переписывания

1. Сначала остановить все обходные записи в модель и команды UPS.
2. Ввести доменные dataclass рядом с текущим кодом без перемещения файлов.
3. Перевести один полный путь `raw polls -> event -> assessment -> recorded_only`.
4. Сделать состояние `BatteryModel` приватным и оставить методы `apply_capacity_proposal()` и
   `reset_baseline()`; старый CLI `--new-battery` вызывает только второй.
5. Сначала перевести `CapacityCandidate` без изменения модели, затем
   `CapacityUpdateProposal` с независимой моделью тока и защитой направления.
6. Удалить старые setters, `calibration_write()` и мёртвый completion pipeline только после
   отсутствия production callers.
7. Разносить файлы по доменным каталогам лишь когда границы уже работают; физическое перемещение
   кода не считается архитектурным результатом.

В Releases A–C новые каталоги `domain/application/infrastructure` не создаются: границы сначала
доказываются типами, импортами и тестами в существующей структуре. Физическое перемещение файлов
рассматривается только после второго реального use case по правилу трёх. Новые generic `utils`,
`helpers`, service locator, event bus и dependency-injection framework не нужны.

## 4. Качество данных

Перед любым практическим расчётом требуются:

- стабильный `event_id`;
- явное начало и конец события;
- отсутствие `CAL`/самотеста для естественного события;
- отсутствие разрыва после перезагрузки;
- монотонное прошедшее время, записанное от `time.monotonic()`;
- конечные правдоподобные напряжение и нагрузка;
- одинаковая длина рядов;
- сырой статус `OB` на всём используемом участке;
- сохранённые сырые и сглаженные значения;
- не менее 90% ожидаемых 10-секундных точек;
- ни одного промежутка между точками больше 25 секунд;
- нагрузка больше нуля и в диапазоне 0–100%;
- замороженная копия параметров модели, использованных при расчёте события.

Для терминального кандидата стартовая запись дополнительно содержит снимок
`ChargeReadinessTracker`. Он обновляется на каждом успешном OL-poll и сбрасывается при OB, CAL,
пропуске чтений больше двух poll intervals или перезапуске процесса. Снимок содержит boot ID,
монотонную длительность непрерывного OL, количество точек, min/max зарядного напряжения и
максимальный gap. Перезапуск внутри требуемых 12 часов консервативно означает «полный заряд не
доказан»; отдельное постоянное хранилище для OL-истории в первом срезе не создаётся.

Начальные аппаратные ворота фиксируются константами, а не россыпью config knobs: raw battery
voltage всё 12-часовое окно находится в 13.0–14.5 В, размах последних 30 минут не больше 0.30 В,
max gap не больше 25 секунд. Перед имплементацией эти числа прогоняются по сохранённому OL-fixture;
изменение порогов требует отдельного тестового доказательства, а не подгонки под один блэкаут.

Для частичного обучающего события дополнительно:

- длительность не менее 300 секунд;
- не менее 31 точки;
- наблюдавшееся изменение напряжения достаточно велико, чтобы превышать шум;
- нагрузка не скачет настолько, что сравнение с замороженной моделью теряет смысл;
- вычисленная старой моделью разница уровня заряда может использоваться только как фильтр
  качества, но не как независимая правильная метка.

## 5. Минимальный полезный алгоритм

### 5.1 Наблюдение частичного разряда

Для качественного естественного участка считать:

```text
delivered_ah_proxy = integral(
    load_percent / 100 * nominal_power_watts / nominal_voltage,
    monotonic_elapsed_seconds
)
```

Сохранять именно `delivered_ah_proxy`, а не `capacity_ah`. Рядом хранить:

- длительность;
- покрытие точками и максимальный разрыв;
- среднюю, минимальную, максимальную нагрузку и её разброс;
- начальное, конечное и минимальное напряжение;
- причину завершения;
- параметры модели, замороженные в момент начала;
- причины принятия или отклонения.

### 5.2 Проверка физической модели

Stage 2 сначала реализует маленький чистый forward simulator, являющийся обратным применением уже
существующих формул, а не новой моделью:

```text
initial_soc = soc_from_voltage(ir_compensate(first_voltage, first_load), frozen_lut)
for each monotonic interval:
    full_runtime_sec = runtime_minutes(
        soc=1, load=observed_load, rated_capacity, frozen_capacity_scale, frozen_peukert
    ) * 60
    predicted_soc -= delta_t / full_runtime_sec
    predicted_v_norm = voltage_from_soc(predicted_soc, frozen_lut)
    predicted_voltage = predicted_v_norm - frozen_ir_k * (load - reference_load)

voltage_residual = observed_voltage - predicted_voltage
slope_residual = observed_delta_voltage / delta_t - predicted_delta_voltage / delta_t
```

`voltage_from_soc()` — только линейная инверсия замороженной LUT с теми же clamp-правилами.
Golden fixtures фиксируют расчёт по шагам. Это диагностические результаты, а не новый сигнал и
не новый параметр модели; «предсказанная длительность участка» без определённой конечной точки
больше не используется.

- сравнивается только реально наблюдавшийся участок;
- возвращение сети означает цензурированное наблюдение, а не фактический полный runtime;
- вычисленный самой LUT уровень заряда не становится правильной меткой для LUT;
- виртуальный `LB` не становится независимой правильной меткой;
- один общий множитель времени не создаётся;
- отчёт показывает, где именно модель разошлась с наблюдением: напряжение, скорость падения,
  нагрузка или ожидаемый конечный участок;
- если данных недостаточно различить причины, событие получает `recorded_only`.

### 5.3 Обновление только определимого параметра

| Параметр | Независимое доказательство | Что не является доказательством |
|---|---|---|
| LUT «напряжение → заряд» | Независимо известные начало/конец и накопленный заряд полного терминального пути; подтверждение второй сопоставимой кривой | SoC, вычисленный текущей LUT |
| Доступная ёмкость | Полный путь до независимого физического конца и достаточно достоверная оценка тока | Частичный разряд до возвращения сети или виртуальный LB |
| SoH | Принятая доступная ёмкость и явная базовая ёмкость | Падение напряжения само по себе |
| Peukert | Несколько подтверждённых разрядов при существенно разных нагрузках | Один partial или время до возвращения сети |
| IR | Отдельный скачок нагрузки уже внутри OB со стабильными окнами до/после | Первичный OL→OB провал после снятия зарядного напряжения |

Два совпавших `delivered_ah_proxy` подтверждают повторяемость, но не устраняют общую ошибку
`load %`, потерь инвертора и собственного потребления UPS. Поэтому они создают только
`CapacityCandidate`. `CapacityUpdateProposal` разрешён лишь при независимо откалиброванном
преобразовании load→battery-current либо измеренном токе, записанном вместе с версией калибровки
и границами ошибки. Предложение меняет только `capacity_ah_measured`; SoH выводится из него.

### 5.4 Признак снижения доступного запаса

Не называть его абсолютным SoH и не выводить из общего коэффициента времени.

- Первое качественное терминальное событие создаёт кандидата доступной ёмкости при конкретной
  нагрузке.
- Два сопоставимых события могут дать статус `possible_decline`.
- Три сопоставимых события дают статус `declining`, если снижение устойчиво.
- Сопоставимость: отдельные периоды полного заряда, средняя нагрузка отличается не более чем на
  10 процентных пунктов, одинаковый независимый конечный маркер и одинаковые ворота качества.
- Отчёт: «доступный запас при похожей нагрузке снизился примерно на X%».
- До достаточного количества событий отчёт говорит `insufficient_evidence`, а не `100% SoH`.

## 6. Длинные естественные события

Первый длинный разряд остаётся кандидатом. Для `natural_terminal_candidate` нужны:

- persisted в start-record снимок `ChargeReadinessTracker`: не менее 12 часов непрерывного OL в
  одном boot без недопустимых gaps;
- стабильное зарядное напряжение в этом окне по явно заданному диапазону и разбросу;
- не менее 15 минут целостного наблюдения;
- отсутствие `CAL`, разрывов и деградации журнала;
- приемлемая и достаточно стабильная нагрузка;
- независимый физический конечный признак: сырой `LB` физического UPS, аппаратное отключение
  либо иной отдельно подтверждённый маркер.

Собственное виртуальное `LB` хранится как `natural_policy_endpoint`, потому что оно вычислено
самой моделью и не может подтвердить её правильность.

Длинное событие сохраняет:

- доступное время до подтверждённого конечного маркера;
- `delivered_ah_proxy` при конкретной нагрузке;
- составную уверенность, ограниченную сверху `0.5` из-за оценки тока через `load %`;
- кандидат кривой разряда;
- снимок готовности заряда и версию модели load→current, если она существует.

Повышение кандидата требует двух независимых событий после отдельных полных зарядов:

- средняя нагрузка отличается не более чем на 10 процентных пунктов;
- оценки доступного заряда согласуются в пределах 15%;
- оба события имеют полный и непрерывный набор доказательств.

Даже после этого результат называется «кандидат доступного запаса при данной нагрузке». Он не
записывается в `capacity_ah_measured` и не становится SoH без независимой калибровки тока.

Кандидат независимой LUT можно построить только для полного терминального пути:

```text
usable_soc[i] = 1 - cumulative_delivered_ah_proxy[i] / total_delivered_ah_proxy
```

Один путь LUT не меняет. После согласия второго сопоставимого пути можно предложить по одной
точке на каждые 10% уровня. Продвижение таких точек в рабочую LUT — отдельный проверяемый этап.

## 7. Этапы имплементации

### Этап 0. Зафиксировать безопасность и правду

**Изменения**

1. `src/scheduler_manager.py`
   - режим по умолчанию — только предложение теста;
   - отправка `upscmd` запрещена структурно в `capture_only`;
   - попытка отправки отражается как ошибка режима.
2. `src/sag_tracker.py`
   - перестать изменять `ir_k`, `rls_state.ir_k` и `r_internal_history` по OL→OB;
   - возвращать неизменяемое наблюдение для журнала;
   - будущий расчёт IR по отдельному скачку нагрузки внутри OB оставить вне первого выпуска.
3. `src/monitor.py`
   - ожидаемое отклонение обычного события завершать как `recorded_only`, не `pending_replay`;
   - перед replay явно отображать старые `evidence_class="operational"` и старые lifecycle в
     новые классы; старое штатное событие не пытается обучаться;
   - ввести один явный режим `capture_only`, включённый по умолчанию на первом выпуске.
4. `src/virtual_ups.py`, `src/virtual_ups_exporter.py`
   - путь вывода обязателен ниже точки сборки production-приложения;
   - только `main()` знает боевой `/run/...`;
   - тесты и утилиты обязаны передавать приватный путь.
5. До открытия модели, журнала и `/run`-выходов процесс открывает с `O_NOFOLLOW`, проверяет права
   и удерживает `fcntl.flock(LOCK_EX | LOCK_NB)` на `model_dir/monitor.lock`. Все writer-entrypoints
   используют тот же lock; второй процесс завершается до первой записи.
6. `READY=1` не считать барьером для upsmon. При доступном NUT сначала записывается свежий virtual
   status, затем READY. При недоступном NUT процесс остаётся живым, выставляет
   `startup_degraded=true`, сохраняет прежнее консервативное состояние и продолжает bounded
   polling. Перед `TimeoutStartSec` он посылает READY с явным degraded STATUS, чтобы systemd не
   создал restart loop. Нельзя подменять неизвестное состояние на `OL`; upsmon не знает про READY,
   поэтому остаточное окно старого LB и возможный консервативный shutdown показываются как
   известное ограничение. Плановый deploy/restart разрешён только после preflight `physical OL`.
7. Определить `scientific_fingerprint` как canonical JSON только полей `soh`, `soh_history`,
   `capacity_estimates`, `capacity_ah_measured`, `physics`, `lut`, `r_internal_history`,
   `battery_install_date`, `new_battery_detected` и `new_battery_detected_timestamp`. Счётчики
   событий и scheduler state в него не входят.

**Отдельная миграция существующего `ir_k`**

До Release A сохранить модель и офлайн сравнить прогнозы для текущего `ir_k`, `k=0` и выбранного
консервативного значения на зафиксированных нагрузках. Пока решение не принято, safety использует
временный консервативный envelope `min(runtime_with_persisted_k, runtime_with_k_zero)`, поэтому
переход не может отложить LB. Это не обучаемый коэффициент и удаляется после отдельного решения по
IR. История сырых наблюдений не удаляется; Release A блокируется, если направление эффекта не
проверено golden-тестом.

**Приёмка**

- короткий блэкаут меняет только журнал и счётчики;
- хеш научных полей модели не меняется;
- никакой код в `capture_only` не вызывает `send_instcmd`;
- при доступном NUT свежий virtual status записан до READY;
- при недоступном NUT нет ложного OL и restart loop, а degraded/возраст status видны оператору;
- второй писатель не стартует;
- штатно отклонённое событие после перезапуска не остаётся `pending_replay`.

### Этап 1. Полный контракт доказательств

**Файлы**

- `src/discharge_types.py`: `LearningDecision`, решения по полям, итог обработки;
- новый небольшой `src/discharge_evidence.py`: чистая классификация события без путаницы с
  существующим `event_classifier.py`;
- `src/discharge_collector.py`: `ChargeReadinessTracker`, монотонное прошедшее время, сырой статус,
  CAL/LB, качество старта, покрытие и максимальный разрыв;
- `src/discharge_journal.py`: однозначный replay без изменения `SCHEMA_VERSION=1` и закрытого
  набора `start/sample/end/applied`;
- `src/monitor.py`: маршрутизация без научных изменений.

`recorded_only`, `rejected` и реальное изменение записываются payload-полем `disposition` уже
существующего `applied` record. Для результата без изменения туда кладётся текущий persisted model
hash. Старый daemon увидит знакомый `applied` и безопасно пропустит событие. Новые record types и
schema bump до отдельной двусторонней миграции запрещены.

Legacy mapping является частью чистого classifier и единственным источником одновременно для
`CompletedDischarge` и end/applied payload:

- старый `operational` + короткая длительность → `operational_short`;
- старый `operational` + не менее 5 минут → `operational_partial`;
- `closed_restart_recovered` или reboot gap → `operational_gapped`;
- старые `operational_partial` сохраняют смысл.

**Приёмка**

- каждое закрытое событие имеет класс, решения и причины;
- неизвестный или повреждённый формат ничего не обучает;
- повторный replay даёт тот же результат;
- старые реальные journal fixtures получают окончательный disposition без изменения старых строк;
- rollback-код понимает весь журнал, созданный Releases A–C;
- настенные часы могут прыгнуть, но длительность остаётся правильной;
- разрыв после перезагрузки никогда не интегрируется.

### Этап 2. Теневая проверка физической модели

**Файлы**

- новый небольшой `src/model_evaluation.py`: чистые forward simulator, proxy и отклонения;
- `src/discharge_handler.py`: отдельный `record_operational_discharge()`;
- `src/model.py`: неизменяемый снимок параметров без новых обучаемых коэффициентов;
- `src/monitor_config.py`: один режим `capture_only`, без набора экспериментальных ручек;
- `scripts/battery-health.py`, `src/motd_status.py`, health JSON: результат понятным языком.

В этом этапе модель только проверяется:

```text
Естественное событие: принято для проверки
Данные: 9 минут, средняя нагрузка 21%, покрытие 98%
Расхождение: напряжение ниже прогноза на 0.18 В к концу участка
Решение: recorded_only — данных недостаточно выбрать ошибочный параметр
Ёмкость / SoH / Peukert / LUT / IR: не изменены
```

**Приёмка**

- фиксированный replay выдаёт ожидаемые отклонения и причины решения;
- fixture проверяет каждый шаг simulator: initial SoC, predicted SoC, inverted LUT voltage,
  обратную IR-поправку, voltage/slope residual;
- self-test, CAL, gap, короткие, шумные и некорректные события отклоняются;
- модель прогноза и безопасное выключение байт-в-байт ведут себя как до этапа;
- partial событие не может создать `CapacityUpdateProposal`;
- пользователь видит результат, а не только внутренний лог.

### Этап 3. Один владелец модели и типизированные кандидаты

**Файлы**

- `src/model.py`: приватное состояние, sanctioned `reset_baseline()` и будущая точка применения
  capacity proposal;
- `src/model_evaluation.py`: `CapacityCandidate` из терминального события;
- `src/discharge_handler.py`: assessment -> residuals -> candidate -> decision и один атомарный
  save с event-ID dedup;
- `src/monitor.py`: orchestration без прямого доступа к model state;
- `scripts/battery-health.py`: решение, кандидат, ограничения и источник.

**Правила**

- обычный partial всегда заканчивается `recorded_only`;
- первое терминальное событие создаёт только кандидата и не меняет модель;
- второй согласующийся кандидат подтверждает повторяемость, но не точность proxy и также не меняет
  модель;
- кандидаты и cohorts являются проекцией существующего journal, а не новыми ключами model.json;
- SoH изменяется позднее только как следствие принятой ёмкости и явной rated-базы;
- safety policy читает только уже сохранённую модель и не участвует в commit;
- `--new-battery` вызывает sanctioned `BaselineReset`, а не прямые записи;
- capture/evidence/evaluation не могут импортировать mutable state; запрет остальных прямых
  setters включается по мере перевода реальных callers, а не фиктивно одним большим тестом.

**Приёмка**

- первое доказанное терминальное событие создаёт кандидата, но не предложение;
- второй согласующийся кандидат создаёт cohort со ссылками на оба события, но model hash не меняет;
- replay кандидата не создаёт дубликат;
- ошибка save результата полностью возвращает память в исходное состояние;
- partial, CAL и gapped события не меняют модель;
- safety output до и после архитектурного перехода совпадает при одинаковом снимке модели;
- отчёт показывает событие, которое вызвало изменение.

### Этап 4. Относительное ухудшение и терминальные кандидаты

1. Добавить статусы `insufficient_evidence`, `possible_decline`, `declining`.
2. Сравнивать только сопоставимые события.
3. Добавить отдельный cohort для `natural_terminal_candidate`.
4. Никогда не смешивать proxy естественного события с controlled-capacity cohort.
5. После двух согласующихся терминальных событий показывать доступный запас при данной нагрузке.
6. После трёх сопоставимых практических событий разрешить устойчивый сигнал ухудшения.

**Приёмка**

- первое событие не создаёт тревогу;
- несопоставимые нагрузки не образуют тренд;
- два согласующихся терминальных кандидата получают статус `corroborated`;
- ни один из них не становится паспортными Ah или абсолютным SoH;
- отчёт объясняет количество доказательств и ограничения.

### Этап 5. Авторитетная ёмкость и первое изменение модели

Этот этап не блокирует полезность естественных блэкаутов.

- исправить контракт `CapacityEstimator`: различать отданный на участке заряд и оценку полной
  ёмкости;
- `CapacityUpdateProposal` требует независимо принятой модели тока/потерь либо измеренного тока,
  версии этой калибровки, границ ошибки и двух evidence event ID;
- версия load→current calibration и её error bounds живут в `config.toml`/операторском протоколе,
  а не в learned model state;
- допустимая независимая основа — battery-side current sensor либо стендовая калибровка минимум в
  трёх точках нагрузки, покрывающих диапазон события, с верхней границей относительной ошибки 10%;
  AC-output smart plug без учёта собственного потребления UPS и КПД инвертора недостаточен;
- proposal меняет только существующий `capacity_ah_measured`; новый state key не добавляется;
- runtime продолжает получать rated capacity в Peukert и производный
  `soh = capacity_ah_measured / rated_capacity_ah`, поэтому ёмкость не учитывается дважды;
- автоматическое применение допускает только уменьшение и перед commit сравнивает старый/новый
  runtime на всём golden-наборе: ни один LB не может стать позже;
- увеличение возможно только через `BaselineReset` или отдельно подтверждённое оператором
  авторитетное измерение; снижение не включает `new_battery_detected`;
- прежнее сравнение `capacity_ah_measured` с convergence не может автоматически объявить новую
  батарею: replacement становится отдельным подозрением, а подтверждает его только
  `BaselineReset`; legacy capacity estimates не смешиваются с natural cohorts;
- Peukert требует нескольких доказанных разрядов с разными нагрузками;
- контролируемый тест не запускается автоматически и требует отдельного разрешения;
- model save предшествует `applied` marker, replay дедуплицируется по обоим evidence ID;
- rollback версии сопровождается совместимой моделью: Releases A–D не добавляют state keys, а
  откат после изменения capacity использует сохранённый pre-change snapshot, не старый бинарник с
  неизвестной схемой.

## 8. Набор тестовых данных

Тестировать не готовые объекты, а сырые последовательности чтений UPS. Каждая строка содержит
детерминированные wall time, monotonic time, boot ID и сырые NUT-поля. Ожидаемые результаты
хранятся отдельно.

Обязательные сценарии:

1. короткий естественный `OL -> OB -> OL`;
2. качественный 10-минутный частичный разряд;
3. длинный разряд, проходящий старые duration/DoD ворота, но не становящийся capacity test;
4. CAL/quick self-test;
5. неизвестное входное напряжение 1–99 В;
6. переставленные флаги статуса, включая `LB OB DISCHRG`;
7. `OB -> OL -> OB` как два event ID;
8. SIGTERM во время OB;
9. перезагрузка во время OB с тем же event ID и явным gap;
10. старт после восстановления сети и закрытие старого partial;
11. оборванная последняя строка журнала;
12. повреждение в середине, повтор seq, неизвестная схема, превышение размера;
13. полное controlled-capacity событие с разрешением capacity/SoH, но без автоматического
    разрешения Peukert;
14. повторный replay и сбои до/после model save и applied marker;
15. старый боевой `.dev` с `OB DISCHRG LB` при старте;
16. два одновременных писателя;
17. тестовый subprocess с очищенным окружением, всё равно не способный получить боевой путь;
18. старый journal с `evidence_class="operational"`, `operational_partial` и
    `closed_restart_recovered`;
19. 12 часов стабильного OL, OL с большим gap, restart внутри окна и нестабильное зарядное
    напряжение;
20. NUT недоступен дольше `TimeoutStartSec`: нет ложного OL и restart loop;
21. сравнение persisted `ir_k`, `k=0` и временного conservative envelope на нагрузках 0–100%;
22. два совпавших proxy-кандидата без current calibration: cohort есть, proposal отсутствует;
23. calibrated-current proposal вниз, попытка proposal вверх и `BaselineReset`;
24. одинаковые входы до/после capacity migration: нет двойного учёта capacity×SoH и LB никогда
    не становится позже.

Golden-результат включает:

- lifecycle, класс и event ID;
- число точек, известную длительность и gap;
- решения по каждому полю и причины;
- итоговый статус обработки;
- хеш научной части модели до/после;
- проекцию журнала;
- отклонения замороженной модели;
- типизированное предложение либо явную причину его отсутствия;
- старое/новое значение только при применённом предложении.

## 9. Инварианты и fault injection

### Инварианты

- первая OB-точка всегда записана;
- seq непрерывен, end не более одного, существующий `applied` marker только после end и содержит
  окончательный disposition;
- открыт не более чем один event;
- длительность одного boot использует monotonic time;
- gap никогда не интегрируется;
- operational event при любом replay не меняет запрещённые поля;
- кандидат без независимой current calibration никогда не меняет модель;
- принятое типизированное предложение применяется ровно один раз и только в сторону меньшего
  либо равного runtime;
- при изменении модель сохраняется до applied marker; при `recorded_only/rejected` marker хранит
  неизменившийся persisted hash;
- ошибка расчёта/save не меняет живые объекты;
- счётчики происходят только из проекции журнала;
- `capture_only` не может отправить команду UPS или вызвать научные setters.
- capture/evidence/safety модули не импортируют изменяемую реализацию `BatteryModel`;
- каждый тип предложения изменяет ровно свой allowlist полей.
- process-wide lock удерживается до закрытия всех writer-ресурсов;
- `scientific_fingerprint` не меняется от scheduler/counter/reporting updates.

### Сбои

- `fdatasync`, ENOSPC, EROFS, permissions, symlink, лимит журнала;
- ошибка start/sample/final sample/end;
- смерть процесса после sync, после model save, до/после applied marker;
- ошибка атомарной записи модели или sync каталога;
- NUT timeout, оборванный ответ, отсутствующие/невалидные поля;
- SIGTERM сразу после OB и сразу после OL;
- отказ health endpoint при исправной публикации virtual UPS;
- stale LB при рестарте;
- NUT недоступен при старте дольше systemd startup timeout;
- параллельный писатель.

Ошибка журнала должна быть видимой, но не задерживать публикацию настоящего LB и безопасное
выключение.

## 10. Изолированный end-to-end smoke

Использовать:

- fake NUT client;
- временные model/journal пути;
- явно переданный приватный `.dev`;
- явно переданные приватные health/MOTD/output пути;
- выключенную отправку команд scheduler;
- реальные classifier, collector, journal, replay, decision, exporter и serializer.

Запрещено в smoke:

- `/run/ups-battery-monitor`;
- `/etc/nut`;
- `upscmd`;
- `systemctl`, sudo и физический UPS;
- второй daemon рядом с production.

Все временные ресурсы удаляются после smoke.

## 11. Выпуск

### Release A: safety + capture-only

1. Снимки и checksums модели, журнала, unit, NUT config и `upsmon.conf`.
2. Физический и виртуальный UPS показывают online.
3. Нет активного события и `shutdown_imminent`.
4. `journal_healthy=true`, `pending_replay=false`, health свежий.
5. Автоматическая отправка теста структурно выключена.
6. Перезапускается только monitor service; NUT topology не меняется.
7. 24 часа наблюдения, включая scheduler hour и один контролируемый restart monitor service.

Pass:

- нет `upscmd`, FSD, неожиданного LB, reboot или рестарта NUT;
- boot ID тот же;
- журнал здоров;
- virtual online согласован с physical online;
- хеш запрещённых полей модели неизменен;
- при доступном NUT после restart новый status записан до readiness;
- при недоступном NUT процесс не объявляет OL, не уходит в restart loop и явно показывает возраст
  сохранённого status.

### Release B: shadow model evaluation

- расчёт отклонений включён, применение предложений выключено;
- replay всех golden fixtures совпадает;
- каждое событие получает понятное решение и причины;
- 24-часовой canary не меняет прогноз и научные поля.

### Release C: terminal candidates and decline trend

- включается только после прохождения A и B;
- первый тип — `CapacityCandidate` из доказанного терминального события;
- два согласующихся кандидата создают cohort и trend, но не меняют модель;
- partial и virtual-LB события не могут создать кандидата;
- replay утверждённого terminal fixture доказывает классификацию и дедупликацию;
- production-доказательство требует journal event, decision, отчёт и неизменный scientific hash.

### Release D: authoritative capacity proposal

- включается только после появления независимой load→battery-current calibration или измеренного
  тока и прохождения Release C;
- меняется только `capacity_ah_measured`, SoH выводится из rated baseline;
- automatic path принимает только уменьшение; golden differential доказывает, что runtime/LB нигде
  не становятся позже;
- model save, applied marker, replay и rollback fault-injection проходят как одна транзакция;
- первое production-применение требует обоих evidence ID, версии current calibration, границ ошибки,
  старого/нового значения и pre-change snapshot.

Не вызывать реальный блэкаут. Прохождение тестов не выдавать за доказательство реального NUT.

## 12. Наблюдаемость

Добавить в health JSON и человекочитаемый отчёт:

- режим обновления модели;
- последний event: ID, класс, lifecycle, число точек и время закрытия;
- итог обработки и причины;
- последний processing marker и отдельно последнее реальное изменение модели;
- краткие отклонения замороженной модели;
- тип последнего предложения и его evidence event IDs;
- последний capacity candidate/cohort и наличие независимой current calibration;
- старое и новое значение изменённого физического параметра;
- хеш запрещённой научной части модели;
- boot ID и revision daemon;
- размер/число записей журнала, ошибки sync и задержку sync;
- состояние доказательств ухудшения батареи.

Тревоги:

- unhealthy journal;
- health старше двух poll intervals;
- открытое событие не получает seq дольше двух sample intervals;
- event остаётся открыт при raw OL больше двух polls;
- pending replay дольше startup grace;
- научное применение из неразрешённого класса;
- изменение научного хеша в capture-only;
- команда UPS в capture-only;
- virtual LB/FSD при physical OL;
- restart loop или неожиданный boot ID.

Event ID не использовать как Prometheus label.

## 13. Откат

Триггеры немедленного отката:

- неожиданное LB/FSD;
- stale safety output;
- деградация журнала;
- изменение запрещённых полей в capture-only;
- команда UPS;
- restart loop или reboot;
- второй писатель.

Порядок:

1. сохранить текущие модель, журнал, логи и checksums;
2. подтвердить, что physical UPS online;
3. вернуть известную версию monitor code/unit;
4. перезапустить только monitor service;
5. проверить свежие physical/virtual status и health;
6. не обрезать журнал: Releases A–D сохраняют schema v1 и старые record types;
7. если Release D менял capacity, восстановить проверенный pre-change model snapshot перед запуском
   бинарника, для которого новая семантика ещё неизвестна;
8. NUT services не перезапускать без отдельного доказательства их неисправности.

Soft rollback нового обучения: применение `CapacityUpdateProposal` выключается, а journal,
residuals и уже сохранённая модель остаются доступными для разбора. Автоматически откатывать
отдельный физический параметр без проверки нельзя.

## 14. Что сознательно не делать

- не разрешать обычному partial событию менять SoH, абсолютную capacity, Peukert, LUT или IR;
- не возвращать `calibration_write()` с model-derived SoC;
- не запускать deep/quick test автоматически;
- не строить ML, Bayesian framework, survival model, load-bin matrix или temperature model;
- не импортировать Grafana данные автоматически в модель;
- не считать длительность блэкаута полным runtime, если вернулась сеть;
- не считать виртуальный LB независимым физическим концом батареи;
- не смешивать natural proxy и controlled capacity samples;
- не применять два совпавших proxy-кандидата как научную ёмкость без независимой current
  calibration;
- не добавлять общий runtime factor или иной множитель поверх физической модели;
- не объединять обучение модели, NUT topology и shutdown thresholds в один выпуск;
- не использовать полный pytest как доказательство безопасности production;
- не запускать второй shadow daemon на тех же файлах.

Опционально позже: IR по отдельному изменению нагрузки внутри OB — стабильные окна до и после,
изменение нагрузки не менее 10 процентных пунктов, переход до 30 секунд и расчёт
`R = -delta_V / delta_I`. Это не входит в первый рабочий путь.

## 16. Определение готовности проекта

Практический этап проверки готов, когда один качественный естественный partial blackout:

1. записан целиком;
2. получил окончательное решение с причинами;
3. показал отклонения текущей физической модели;
4. не создал предложение без независимого доказательства конкретного параметра;
5. не изменил SoH, capacity, Peukert, LUT, IR или new-battery;
6. не повлиял на safe shutdown;
7. виден пользователю без чтения исходников и journal JSON.

Практический этап наблюдения деградации готов, когда два сопоставимых доказанных терминальных
естественных события:

1. создали двух кандидатов, согласующихся в заданном допуске;
2. создали один cohort со ссылками на оба event ID;
3. показали повторяемый доступный запас и возможный тренд;
4. после restart/replay не продублировались;
5. не изменили scientific fingerprint или safe shutdown без независимой current calibration.

Практический этап изменения модели готов, когда этот cohort вместе с независимой current
calibration:

1. создал ровно один `CapacityUpdateProposal` со ссылками на оба event ID и версию калибровки;
2. изменил только `capacity_ah_measured` одним атомарным commit;
3. пересчитал SoH как производное от rated capacity без двойного учёта;
4. после restart/replay не применился повторно;
5. не сдвинул ни один golden runtime/LB позже;
6. оставил audit старого/нового значения и обратимый pre-change snapshot.

Оценка падения батареи готова, когда несколько сопоставимых событий дают объяснимый тренд с
указанным количеством доказательств. Абсолютная ёмкость и SoH остаются отдельной, более строгой
возможностью и не блокируют этот результат.
