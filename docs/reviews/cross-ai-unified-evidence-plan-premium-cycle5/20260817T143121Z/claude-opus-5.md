### MEDIUM

**M1 — The 2 MiB terminal reserve is asserted but has no bounded inputs, and the current line cap gives it only ~16 records of room.**
plan:184–186 requires proof that the "maximum canonical sum of every post-capture record" fits in 2 MiB. Nothing freezes the *cardinality* of that tail. Assessments are per-fragment and per-consumer by design (plan:99–103), fragment count grows with aggregate length, and a 62 MiB aggregate can hold hundreds of thousands of samples. `DischargeFragmentPolicy` (plan:363–367) freezes only "per-fragment sample/event budgets", not per-aggregate derived-record counts, and `MAX_LINE_BYTES = 128 * 1024` (`jsonl_record_codec.py:28`) applies to derived records — 2 MiB is 16 such lines. Worse, `append_capacity_exceeded` applies `CAPTURE_APPEND_LIMIT` only when `record_type == "observation"` (`jsonl_event_capacity.py:232`), so every derived append is checked against the hard 64 MiB and raises `_EventCapacityExceeded` on overflow. Freeze max fragments per aggregate, max assessments/comparisons/estimates per fragment, and a derived-record size cap, and make the sum a construction-time invariant — the same treatment the plan already gives recharge.

**M2 — The recharge byte proof is arithmetically ambiguous and has an unbounded term.**
plan:233–235 requires `max_samples * max_physical_record_size` plus START, gaps and "the full maximum derived/terminal tail" to remain "below the 62 MiB capture-append limit with the 2 MiB terminal reserve intact". That double-counts: the terminal tail is what the 62–64 MiB reserve exists for, so the invariant is satisfiable two different ways with a ~2 MiB discrepancy — unacceptable in a numeric constraint that is being frozen into construction-time code. Separately, "gaps" carries no maximum count. `recharge_gap` is emitted per recovery/restart (plan:252–260), mid-chain gaps may recur while identity is reattachable (plan:240–243), and recharge has no rollover, so the only bound on gap records is the number of restarts. State which side of the 62/64 MiB split the tail is charged to, and freeze `max_gap_records` per episode.

**M3 — The reserved 64th reference has no named enforcement point, and an over-reservation permanently bricks the aggregate.**
The ref limit is enforced today only when reading: `event_total_bytes` raises `_EventCapacityExceeded` when `len(sources) > MAX_SEGMENT_REFS` (`jsonl_event_capacity.py:191-193`). `reserve_segment_manifest` (`jsonl_event_capacity.py:102-130`) and `_create_continuation_segment` (`jsonl_event_stream.py:348`, `392`) perform no count check at all. If a 65th manifest entry is ever reserved, `segment_sources`/`event_total_bytes`/`validate_before_full_read` raise on *every* subsequent read, so the whole chain — including its raw physical samples — becomes unreadable rather than closed. plan:190–191 says not to turn a reachable limit into capture damage or an unhandled exception but never names where the "reference 64 is reserved" check lives. Require the reserve to be enforced at manifest reservation/continuation creation, and add a fixture proving a 65th reservation is refused before bytes exist.

**M4 — The intent-removal gate is undefined for in-window boundaries that never receive a durable START, and for unlinked recharge episodes.**
plan:591–594 acknowledges intent removal only after the capture/prestart/residual registries prove every in-window event start has a durable blackout START stamp. But in-window boundaries can legitimately exist with *no* START at all: prestart FIFO boundaries and `prestart_boundary_overflow` aggregate loss (ADR 0003:26–34, plan:294–300) are receipts, not STARTs. Two bad outcomes follow, neither excluded by the current text: the gate is unsatisfiable and the intent can never be closed, or an implementer treats "no START to stamp" as vacuously satisfied and a later recovered START — written after the intent file is gone — is stamped `natural`. The same hole exists for the unlinked censored recharge episode of plan:208–210: it has no blackout to inherit provenance from, so its origin must come from the intent file that removal deletes. Require in-window prestart/overflow receipts to carry `observation_origin`/`uat_intent_id`, require recovered STARTs and unlinked recharge chains to inherit from the receipt, and specify that the intent record is retained-and-closed rather than deleted while any in-window boundary is unterminalized.

**M5 — A persistently oversize or malformed NUT reply produces one loss record per second with no coalescing bound.**
plan:201–203 freezes a 16 KiB raw-envelope / 20 KiB record ceiling and requires oversize replies to produce "an explicit gap/loss record". `NUTClient._MAX_RECV_BYTES = 64 * 1024` (`src/nut_client.py:106`), so a reply between 16 KiB and 64 KiB parses successfully every poll and would emit a `discharge_gap` at 1 Hz indefinitely. The plan defines coalescing only for prestart boundaries (ADR 0003:26–30) and in-flight/residual receipts for overflow (plan:294–300), not for per-poll envelope rejection. Consequence: a driver/firmware change that widens the reply turns the "near-unreachable" byte rollover into a fast, continuous rollover chain and floods the aggregate with system records. Require the same coalesced receipt (reason, count, first/last boundary) for repeated oversize/malformed replies, and reconcile the 16 KiB freeze against real reply sizes from the Slice-0 baseline before freezing it.

**M6 — Fragment profiling of a 62 MiB aggregate is specified as "bounded" but the only implementation shape materializes the whole event in RAM, inside the safety process.**
`EventProjection` holds every record of every segment (`src/application/storage_values.py:162-172`), built from `_read_all_records` per segment (`jsonl_event_stream.py:326-334`), and consumers take the full tuple (`assessment_worker.py:427`, `520`; `decline_reporting.py:183`; `src/domain/evidence.py:62` iterates the complete observation tuple several times). The plan mandates assessing "long prefixes from deep events" (plan:42–48, 508–511) and permits unlimited linked aggregates (plan:180–181), but sets no per-aggregate record/memory budget for `ProfileEvidence` and no streaming requirement — while background assessment shares the process that owns the one-second safety publication. Add an explicit bounded-memory obligation (streaming fragment profiling with a frozen window budget, reusing `jsonl_large_event_cursor.py`) and a fixture at the maximum aggregate size.
