## Verdict: **NO-GO** (2 High, 4 Medium). Not implementation-ready as written.

The plan is scientifically honest and the anti-feedback/censoring architecture is sound — the scientific review's veto on safe-shutdown-as-endpoint is correct, and per-fragment admission is the right replacement for `TerminalSciencePolicy.authorizes_science`. But two plan-level contradictions would surface as rework mid-implementation, and one unacknowledged product regression means the plan as written can ship "complete" while automatically learning *less* than the tree it supersedes. The prior standard-model GO convergence appears to have validated internal consistency of §§3–7 without tracing the v3 cutover's effect on existing cohorts or on v2 state ownership.

---

### HIGH 1 — V3 cutover preflight requires a v2 reader the same plan forbids
`inputs/unified-...plan.md:258-263` makes deployment conditional on the new binary proving that "the v2 work registry [has] zero open/preparing/processing captures", that every prestart/overflow in-flight and residual receipt slot is empty, and that "the v2 report outbox [is] empty/acknowledged". `:402-404` (Slice 1) states the opposite constraint: "no compatibility reader or reverse migration is added", and §2 `:77-78` forbids backward compatibility outright.

Failure scenario: implementation reaches the cutover task and has three mutually exclusive options — add a v2 registry/outbox reader (violates §2 and Slice 1), skip the preflight (strands or fabricates a v2 terminal outcome, which `:261` explicitly forbids), or invent an unspecified external step. The plan never says *who* runs this preflight. The only consistent design is that the **old binary** self-attests emptiness into a small durable handshake artifact before stopping, and v3 reads only that artifact — but that artifact is not in the plan, has no schema, and is not in the frozen-codec list. This needs resolving before Slice 0, because it changes the Slice 0 baseline/backup contract.

### HIGH 2 — V3 cutover silently resets every learning cohort and decline baseline; not acknowledged
`:220` and `:402-404` cut over to "fresh `events-v3/`" directories, and `:363` scopes only *history queries* to "begin at the v3 cutover", with v2 archives "never silently re-evaluated as v3 science".

But the existing `ir_k` path draws its cohort from the event index: `inputs/assessment_worker.py:372-417` (`_historical_candidates` → `index_tail_for_epoch`, `HISTORICAL_COHORT_LIMIT = 31`), and the three decline signals draw latest-six cohorts the same way (`inputs/decline_reporting.py:111-133`). After cutover both sets are empty. Consequences the plan never states:

- `ir_k` — the plan's own "only currently proved automatic model target" (`:27`) — cannot commit until enough independent v3 blackouts with clean load steps accumulate. Given the operating profile (short outages several times a week, deep events ~2× in 4 years), that is plausibly months, and `min_commit_interval_days=30` (`values.py:161`) sits on top of it.
- All three decline trends return `insufficient_comparable_evidence` for the same period.
- Business outcome `:53-54` ("never needs … an operator decision … for routine learning") is formally met while the system in fact learns nothing for an extended window.

This is a real regression against the 873-test tree, and it is invisible in §13's definition of done. The plan must either state and accept the reset explicitly (with expected blackout-count-to-first-commit), or define a one-way *evidence-preserving* re-projection of v2 raw samples into v3 cohorts — which is a science decision, not a migration, and needs its own §7.1-style justification.

Related and compounding: `:400` requires Slice 1 to "keep current IR result byte-for-byte equivalent for existing qualifying fixtures." Removing the event-wide gate changes historical-cohort membership, because `_historical_summary_is_eligible` (`assessment_worker.py:93-99`) currently *requires* `authorizes_science` on each historical summary. Any fixture whose cohort contains a `service_stop` / `closed_restart_gap` event will produce a different median and a different commit. As written the gate is either vacuous (no such fixture exists) or unsatisfiable. Scope it: "byte-identical for fixtures whose cohorts contain only `power_restored` events; all others get new expected values with recorded rationale."

### MEDIUM 1 — Capture-budget overflow reinvents loss instead of reusing `continued_by`
`:167-175`: at the 64 MiB cap the chain closes as `capture_budget_exceeded` and subsequent samples of the *same still-live physical episode* accumulate in a bounded **RAM-only** counter that "can be lost on hard process/host death." Yet the plan already has a durable mechanism for one physical episode spanning multiple chains — `continued_by` (`:249`, tested at `:463`). Opening a fresh v3 chain linked by `continued_by` would make post-cap capture fully durable and delete a whole accepted-loss class. Choosing RAM-only here contradicts business outcome `:36-39` ("durably captured or represented by an explicit bounded loss/rejection receipt") and is a DRY/design-fit inconsistency with §4.1's own reboot-continuous handling.

Also unresolved: 64 MiB is asserted as a hard authority (`:167`) but no per-record or per-raw-key-map byte bound is frozen anywhere. `:252-254` bounds the raw envelope qualitatively ("Oversize … retain an explicit loss reason") without a number. So the cap has no defined meaning in seconds, and §10's cap test cannot be written deterministically. Freeze the record/envelope bound alongside `DischargeFragmentPolicy`.

### MEDIUM 2 — State-dependent recharge subsampling is declared, not corrected for
`:184-192` makes recharge persistence density a function of observed status/voltage/charge-slope, and `:36-39` says unselected polls are "represented by the policy revision recorded at start." Recording the policy documents the mechanism; it does not make the resulting sample set exchangeable. Sampling density conditioned on the signal is informative (endogenous) sampling: any slope, stabilization-time, or curve-shape statistic computed over those slices is biased relative to the same statistic over uniform 1 Hz data, and the bias direction depends on battery state — exactly the quantity of interest for a degradation correlate. §12's SoH-correlate framing inherits this. Recharge stays diagnostic-only (`:316-318`), which caps severity, but the required §7.1 preregistration for any future recharge target must include a selection-bias term, and §5's information-content gates should carry an explicit "sample selection independent of the estimated quantity, or bias bounded" criterion. Neither exists.

### MEDIUM 3 — `uat_intent` binding is not stated to be single-use
`:480-489`: the intent "binds only when event start is after intent creation and before expiry", expiry capped at one hour, and "Its matched event is permanently operational-only." Nothing says the binding is *consumed* by the first match.

Failure scenario: operator unplugs mains, replugs, unplugs again within the same one-hour intent (a normal way to run a plumbing UAT twice). Read one way, both events are labelled operational-only; read the other way, only the first is, and the second enters natural estimators as induced data — precisely the contamination the intent exists to prevent. Given the plan states elsewhere that admitting induced data is worse than accepted loss (`:488-489`), specify: one intent binds at most one physical episode, is durably marked consumed at first match, and any further event in the window is *also* conservatively excluded until the intent is acknowledged and removed.

### MEDIUM 4 — Shutdown-poll boundary reservation has no bounded-contention path
`:155-157` requires the combined `discharge_sample` + `shutdown_boundary` command to be reserved/enqueued "under the capture submission lock before any subsequent poll can enqueue another sample", while `:146-150` requires safety publication never to wait for storage. The reservation itself is on the poll thread immediately after publication, and the plan bounds *durability* (five-second sticky-LB window) but never bounds **lock acquisition**. If the submission lock is held by a writer blocked in a kernel filesystem operation — a boundary the prior panel explicitly accepted as unfixable (`panel...md:123-125`) — the shutdown poll blocks with no specified deadline or failure path. Specify a bounded non-blocking reservation attempt plus the explicit censored/unhealthy outcome on failure, and add it to the four boundary races at `:151-154`.
