## Verdict: **NO-GO**

The nine amendments are all present in the plan text and most are genuinely closed. But the amendments introduced new specification surface (rollover, recharge backbone, UAT intent lifecycle) that is not internally consistent, and two of those gaps are exploitable rather than cosmetic. The plan is not yet implementation-ready in the "exact plan" sense the gate requires.

### HIGH

**H1 — A consumed UAT intent leaves the induced discharge unlabelled, admitting induced data into natural science.** Plan lines 526–537.

The mechanism is single-use: the first matching event "atomically consumes the intent once," and the conservative widening covers only the interval "until that consumption is durably acknowledged and the intent removed." A natural blackout inside the ≤1 h window therefore consumes the intent and is marked operational-only (correct, per line 531). The intent is then gone. The operator's actual mains-removal run, minutes later, matches nothing and is captured as a natural event with full science authorization. The runbook rule at line 534 forbids inducing loss only "after intent expiry" — not after consumption — so the procedure as written does not prevent this. Line 535–537's accepted-operator-error caveat covers unmarked unplugs, but this is a path the plan itself creates while the operator is following the runbook. This deployment has frequent short outages (several/week), so window collision is not hypothetical.

Fix direction: consumption must either not release the window (intent remains armed until explicit operator cancel or expiry), or a consumed-by-non-target intent must be reported as *unfulfilled* and the runbook must require re-arming before inducing loss.

**H2 — The uniform recharge backbone is a hard admission gate with no field in the policy it is supposed to be frozen in, and no test.** Plan lines 195–197 vs. 203–207 and 492.

Line 196 makes the uniform backbone the *only* admissible sample set for curve/slope/trend evaluators, and §5 line 313 repeats it as an information-content gate. But the mandatory pre-Slice-4 `RechargeSamplingPolicy` freeze (lines 204–207) enumerates `revision`, dense/sparse intervals, slope window, stable band, consecutive windows, vendor flat band, max duration, max samples — there is no backbone interval field. Lines 190–193 additionally describe adaptive dense/sparse as the primary scheme, which reads as an alternative to, not a superset of, a uniform backbone. The deterministic test at line 492 only asserts dense-at-transitions/sparse-when-stable; nothing tests backbone presence throughout the episode or that evaluators consume backbone-only. As written, Slice 4 can pass its own freeze and its own test while making the §5 selection-bias gate unenforceable.

### MEDIUM

**M1 — Rollover identity is ambiguous between "segment" and "new aggregate," and one reading collides with existing storage policy.** Lines 174–178 vs. 262.

Line 175 caps and closes a *segment*; line 262 says `continued_by` "names the exact newer blackout ID." Those are different objects. The existing adapter already has an intra-aggregate multi-segment concept with its own caps — `src/adapters/jsonl_event_capacity.py:192-215` rejects >64 segment refs, event >64 MiB, and segment >64 MiB. Under the segment reading, the first rollover immediately trips the per-event 64 MiB cap; under the aggregate reading, `MAX_SEGMENT_REFS` is irrelevant and the plan never bounds the continuation chain length. Placement of `continued_from` is never specified (only `continued_by`'s placement is, at line 262). An implementer can build either and both are defensible from the text.

**M2 — The history projection cannot satisfy its own episode-counting requirement, and terminal counts double-count rollover.** Lines 386–389 vs. 176–177 and 503–505.

§8's summary field list is: physical episode kind, start/end UTC, duration, terminal anchor, aggregate-loss count, battery epoch, linked recharge ID. There is no `physical_episode_id` and no continuation link, so "History counts the episode ID once" (line 177) and "one physical episode/history count" (line 505) are not achievable from the bounded index scan §8 mandates. Separately, line 243 puts `capture_budget_exceeded` in the same closed enum used for terminal-type counts (line 243), so a single rolled-over outage contributes both a `capture_budget_exceeded` and a `power_restored` terminal. No rule excludes carriers from terminal counts.

**M3 — `continued_by` is overloaded across two physically different continuations with no discriminator.** Lines 176–177 (budget rollover, same boot, no gap) and 217–219 (reboot-continuous outage, gap spans a reboot).

Line 177 instructs assessment to "traverse verified links without integrating across an unproven gap." That predicate is not decidable from the link alone: one continuation kind is gap-free by construction, the other is inherently gap-bearing. Line 176 gives the rollover case a shared `physical_episode_id`; the reboot case (lines 217–219, test at 499) never states whether the split pieces share one. Consequently the calendar-count answer for a reboot-split outage — one event or two — is undefined, which is exactly what business outcome #1 (line 34) promises to be exact about.

**M4 — The cohort reset amendment is silent on the IR learning bookkeeping that enforces cumulative safety bounds.** Lines 291–295.

Line 292 preserves "existing learned model values and safety behavior"; line 293 resets IR and decline cohorts. Neither statement covers the three fields that actually gate cumulative safety: `epoch_initial_k_v_per_pp`, `previous_commit_utc`, `consumed_step_hashes` (`src/application/model_port.py:34-36`). In `src/domain/learning.py:261`, the 50 % per-epoch decrease floor is anchored on `epoch_initial_k_v_per_pp`; re-baselining it at cutover silently reopens the full budget without a battery replacement. In `src/domain/learning.py:214-221`, the 30-day rate limit depends on `previous_commit_utc`; clearing it permits an immediate first v3 commit. Both omissions bias toward *later* shutdown, the direction the plan and ADR 0003 forbid. Because "no reverse migration" is the standing rule, an implementer will plausibly treat these as derived cohort state and clear them.

**M5 — Capability-manifest registration is circular against the mandatory policy freezes.** Lines 61–63, 418–423, 203, 319–322, 466.

§2 requires the probe "before implementation"; Slice 0 line 422 requires "the same typed field and parseable unit in 60 consecutive ordinary physical replies" for first registration, line 423 forbids fixtures from populating the live manifest, and line 420 forces re-registration on "explicit binary schema revision change" — which a v2→v3 cutover is. So the authoritative live manifest can only exist after v3 starts, while the `DischargeFragmentPolicy` (line 319) and `RechargeSamplingPolicy` (line 203) freezes that depend on the registered field set are hard pre-Slice-1/pre-Slice-4 gates, and line 466 forbids deploying before Slices 1–4 ship together. The plan never says which artifact — pre-implementation probe result or post-cutover v3 manifest — is authoritative for the freezes, nor what the freeze contains for a field that registers only after cutover.
